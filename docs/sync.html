How the reduced LiveStore sync engine works

LiveStore syncs events, not database rows. A client session creates local events, a leader orders and persists them locally, and a sync backend enforces the final global order. The hard part is preserving a single total order while clients can work ahead of the backend.

One-Screen Model

The system is hierarchical. Client sessions sync with a local leader; the leader syncs with a backend. Every layer keeps a SyncState with a local head, an upstream head, and pending events.

The backend is the global authority. It accepts events only when their parent equals the backend's current head. If another client already advanced the backend, the push is rejected with ServerAheadError; the leader must pull, rebase pending events, and push again.

The client and leader use composite sequence numbers. The backend only sees global sequence numbers.

Layer Owns Core responsibility
Client session Optimistic state, pending local events, UI-visible sync state Encode events, apply them locally, pull leader payloads, roll back and rebase when needed.
Client leader Durable local eventlog, local materialized state, backend push queue Serialize local pushes, broadcast to sessions, pull backend events, rebase pending leader work.
Sync backend Append-only global eventlog Enforce the total order by accepting only batches that continue the current backend head.

Event Notation

This page uses the notation from LiveStore's contributor docs. The base form is [Client:]e{global}[.{client}][r{rebaseGeneration}]['][/{origin}][{context}].

Events with a non-zero client component, such as e5.1, are client-local. They can move between client sessions and the leader, but they are filtered out before the backend push queue.

The Three Layers

1. Client Session

The session is closest to the application. In this reduced repo, src/client.ts encodes decoded events from the current local head, merges them as local-push, applies reducers optimistically, then pushes the encoded batch to the leader.

2. Client Leader

The leader is the local ordering point. LiveStore's full implementation uses worker and SQLite scaffolding; this repo keeps the ordering behavior in src/leader.ts. It validates local batches against a push head, serializes local pushes against backend pulls, broadcasts upstream payloads to sessions, and keeps a backend push queue for non-client-only events.

3. Sync Backend

The backend is deliberately simple. The Cloudflare sync provider stores events and checks that the first pushed event's parent equals the current backend head. src/fifo-backend.ts preserves that rule with a local FIFO log. 

if (batch[0].parentSeqNum !== currentHead) {
  fail(new ServerAheadError(currentHead, batch[0].parentSeqNum))
}

Happy Path

A single client creates an event while everyone agrees on e1 → e2. The event is first pending locally, then pending in the leader, then confirmed after the backend accepts and emits it back.

The Merge Rules

The core algorithm lives in src/sync-state.ts, corresponding to LiveStore's syncstate.ts. Every layer calls the same merge operation with different payloads.

Payload Meaning Result
local-push A downstream node created events locally. Append to pending if the first event is ahead of local head; otherwise reject.
upstream-advance The upstream node has new confirmed events. Confirm matching pending events, append new upstream events, or rebase divergent pending events.
upstream-rebase The upstream node already rebased and tells downstream how to follow. Roll back listed events plus local pending, apply upstream events, then rebase local pending.

Edge Cases

Concurrent Backend Pushes

Two leaders can both create e3' from the same backend head. The backend accepts the first push. The second push fails because its parent is no longer the backend head. That is not a conflict resolution UI; it is a protocol signal telling the second leader to pull and rebase.

Client-Only Events

Client-only events are still part of the client/leader local chain, but the leader filters them before pushing to the backend. That is why they use the client sequence component: e5.1 follows e5, but the next synced event can still be e6.

Leader Push Head Rejects Duplicate Local Pushes

The leader keeps a push head in addition to SyncState. This prevents two sessions from pushing the same first sequence number before the local push queue has finished processing. If the first event is at or behind the push head, the leader rejects with LeaderAheadError; the client pulls and retries from the updated head.

Stale Rebase Generation

A queued local push can become stale while a backend pull rebases the leader. LiveStore handles this by comparing each queued event's rebaseGeneration with the current local head generation after the pull mutex is acquired. Older queued events fail with StaleRebaseGenerationError so the session can resubmit.

Undefined Args and Wire Round Trips

Event equality canonicalizes args through JSON. Without this, a local pending event with an undefined optional field could compare unequal to the same event after JSON transport, causing a false rebase. This edge case is covered in test/sync-state.test.ts.

Backend Reset Detection

Full LiveStore providers use a backend identity to detect when the backend was reset while clients still have cached local state. This reduced repo omits backend identity because its FIFO backend is in-process, but the production concern is documented in LiveStore's syncing docs.

What This Repo Keeps

The reduced implementation removes platform and storage scaffolding while keeping the protocol behaviors that make sync hard to reason about.

Kept Reduced or omitted
Composite sequence numbers, pending queues, merge/rebase logic, leader push rejection. SQLite eventlog tables, workers, HTTP transports, devtools, OpenTelemetry spans.
Backend append-only parent check and ServerAheadError rebase/retry path. Cloudflare Durable Object storage, WebSocket/RPC transport, backend ID mismatch handling.
Client optimistic materialization, rollback by event removal, deterministic recomputation. SQLite changesets and materializer hashes. The testable state result is the same for pure reducers.
